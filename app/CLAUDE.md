# app/

The Tauri 2 desktop app: the shell in `src-tauri/` (uses `../core` as a library) and the view in `src/`, plain TypeScript built by Vite, no framework. Layout and commands: `README.md`.

## Rules

- The shell never writes to a project. Reading runs on a background thread and reports progress events.
- Every view change works in four looks: light and dark, on macOS and on Windows. The layout is shared; the platforms differ only in the title bar, fonts and accent (`html.mac`, `html.windows` in `styles.css`). Windows has never been built or run, so the browser preview is its only check. Look at all four with the `look` skill after any view change.
- Plain and native, like Zed and Ghostty: the system font for the interface, monospace only for code, one accent, light and dark from the system.
- The view never parses titles or ids. The core carries structured fields (event, control, text, handler; ids are opaque), and the view composes names from them (`model.ts`).
- Ids hold quotes, brackets and any letters: escape them wherever they go (HTML attributes, URLs, file names).

## Traps

- `code.ts`: each line's text is its own flex item (`.ct`). Highlighted spans placed directly in a flex row lose the spaces between them.
- Diagram text widths are measured with the monospace font in a canvas (`ui.ts`). The font sizes in `diagram.ts` and the diagram rules in `styles.css` must stay the same numbers.
- The diagram's SVG shares the stylesheet with the HTML: a class used outside it (`.chip`, `.bar`) also styles, and even sizes, an SVG element. Give diagram classes names of their own.
- The diagram's SVG is drawn at its own size; `canvas.ts` moves and scales it. A drawn element slides when a call opens only if it has a key that stays the same between drawings (`keep` in `diagram.ts`); one without a key just appears.

## Reading rules for the diagram

Decoration comes from structure (depth, parent), never from content.

- **Nesting is told by the numbers, and nothing is painted for it:** a row's number is its place in the story with every call open, as an editor that folds keeps its line numbers. A closed call is followed by a jump (`2`, then `10`) that opening it fills; no number changes when a call opens or closes. Numbers of rows inside an opened call are in the accent color; no band, no indent. A call that opens has a small button over the mark at the end of its words: soft `▸` while closed, filled `▾` when open. Change signs have their own column at the left edge, so they never shift a number. The gutter fits the longest number.
- **Columns are places at one of two levels:** one per place the code runs (device, browser, server, or `Code` where nothing shows the place) plus one per outside service or package, or one per function. A story opens at functions when that makes at most six columns, else at places. Clicking a place opens it into its functions; its label above closes it. Calls inside one column are loops on it.
- **The same columns while reading, spaced for what is shown.** They are every place the story reaches at the level, open or not, in the same order; none appears or goes when a call opens. The room between them fits only the rows shown, so a closed call's insides take none: opening a call can push columns aside, closing it brings them back, and the row clicked stays where it is on screen. A column nothing shown reaches is quieter. The set of columns changes only when the level changes, a place opens or closes, or "every step" is toggled. Closing an arrow leaves no marks behind.
- **A story opens closed.** Only calls holding a change since the user last looked start open. A closed call names on its row what it changes in the data (`· deletes items`), else what it reaches outside the project's code (`· openai`); the panel lists both.
- **Another story is a reference, not a copy.** A step that starts another story (a screen rendered or opened) or hands it work (a job given to a scheduler) is a row on its own lifeline in the link color with `↗` and that story's name, no column; a click goes to that story. What it does is told there, once. A call to an endpoint is not one: the caller waits for the answer, so it opens in place.
- **Every call that changes column returns:** an opened call ends with its return, a closed one shows it under it, and a package call whose result is kept comes back labeled with the name it is given.
- **Rules show where they are written.** A rule (a throw, or a return before its function's end) is a row with its condition in front: a return arrow to the caller, or, on the same lifeline, a row that stops there. A thrown one is in the warm color. A loop's `break` or `continue` is a row with its condition in front and its keyword quiet: that round of the loop ends there. A closed call names how else it can end, from what it calls too (`· or 403, Denied`; a rethrow by what it passes on); a call that changes what it is given or its own object says so (`· changes cart.items`), and a statement that does is a row of its own.
- **The first level shows what a person would notice.** In a story that reaches past its own code, what only the code holds is left out: what the screen holds on the way (what it holds as a way ends, the message before a return, stays), a plain helper that works a value out, side work. A changed step always shows. "every step" shows them all.
- **A call that crosses no boundary is not a column.** A plain function with no body to show and no effect folds with its return into one row (`name(args) → result`), but only when everything between the call and its return belongs to the callee. Calls to one place in a row, with nothing kept, are one row. "every step" turns folding off.
- **Side work is never a column:** a project function whose result is unused, that reaches no table, endpoint or other screen, and that many stories reach (logging, analytics), and that cannot end the work early. Left out at the first level; with "every step", one quiet row. The panel says why.
- **No text crosses a lifeline other than its own.** A step that stays in its column writes to its right; so does the thin divider over what runs later, which says only when it runs ("after first render") and spans only its own rows; an arrow's label sits in the widest gap it crosses; long text is cut and shown whole in the panel.
- **The diagram is a canvas:** a fixed area over a faint grid. A wheel, two fingers, a drag from anywhere or the arrow keys move it, along a side only when it does not fit on it; a pinch or ⌘/Ctrl with the wheel zooms toward the pointer. Lifelines are solid, so they are not read as the grid's dots (one nothing shown reaches is dashed). The column boxes stay at the top while rows move under them; the step numbers stay at the left edge when it is moved across, each beside its row, on one strip from the first row to the last that the rows show through, blurred. A story opens whole when that keeps it at 85% or more, else as wide as the area (never below 85%) from the top, at its first change; a view the user has not moved does the same when the columns move. Opening or closing a call leaves the view where it is: the rows below slide, new ones fade in. Moves the user did not drag are eased.
- **Only what the diagram cannot show is written beside it:** whether tests reach the functions and what changed (above it), where the story can stop (inside closed calls too), grouped by how it ends, what the code warns of, what is not resolved (a tab each in the pane under it, which is resized by dragging its bar and closes down to it). No title over the diagram, no trigger lines, no "A calls B" in the panel; how to read it is the pane's last tab, "How to read this".
- **The story list is the places a person meets** (`places.ts`): the app's start and its layouts, the screens in the order a person reaches them, each opening into its controls under the parts that write them, then the server and the entry points no adapter places, with a filter; the selected story is scrolled into view and its screen open. It is made from structure only: what starts in what, what draws what (`draws` in the index), where a step goes (its reference). A control's row says what it changes, calls and goes to, never the code. Tests have their own tab ("reached by", never "tested"). Names read the way a person says them: the words on the control, else the handler's name in plain words, else the event. A story that starts in more ways says each, by how it differs (`or “Done”`, `or another Pill`, `or field submitted on TextField`), on its trigger row too.
- **The list can narrow to what reaches one thing** (Go to, "N stories reach it", a table in the Data tab), from the model's index only, each story opening at its step. The count says "at least". A click in the diagram opens what it is on; it does not narrow the list.
